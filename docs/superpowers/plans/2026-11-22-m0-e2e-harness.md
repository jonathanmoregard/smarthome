# M0: End-to-end Harness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (default) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An end-to-end harness that drives today's Jinja scripts and the current TypeScript port through the same Home Assistant inputs, and compares where every lamp and switch ends up, with golden scenarios and Hypothesis fuzzing.

**Architecture:** Both backends run inside the existing `DrySim` simulator (reference: the preserved Jinja; port: `DrySim` patched by `tests/parity/adapters.py:simulator` to cross the TypeScript RPC). New Python pieces sit on top: a trigger router turns HA inputs into automation runs, a world model turns recorded service calls into bulb and switch state, and a runner settles each step and takes checkpoints. Comparison is of world state, never of calls.

**Tech Stack:** Python 3.14 (the parity Python, with the HA 2026.7.4 wrapper closure via `tests/parity/portability.py`), `unittest`, Hypothesis (`python314Packages.hypothesis` from the flake's nixpkgs), Node 22 for the port's RPC.

**Spec:** `docs/superpowers/specs/2026-11-22-lighting-architecture-design.md` (sections 6 and 7.1). M1–M6 get their own plans after M0's measurement.

## Global Constraints

1. The repo is public. No household names, area ids, entity ids, device addresses or friendly names in any committed file, commit message or test. Code reads them from the catalog at run time.
2. `reference/`, `.runtime/`, `tests/parity/migration-fixtures.json` and `*report.json` are never committed or quoted. Golden recordings and fuzz failures from the live catalog go to `lighting-scripts/.runtime/e2e/` (already ignored).
3. Compare end state only: per bulb power, level, colour, firmware effect; per switch power; the `sensor.ls_overrides` attributes `switch_ranges` and `range_defaults`. Never compare the exact commands.
4. Tolerances (named constants in `tests/e2e/compare.py`): settled level ±2 steps; kelvin ±50 K; RGB by xy distance ≤ 0.01; mid-fade level ±1 % (`MID_FADE_LEVEL_PCT = 1`).
5. "Green" means zero unexplained differences. A difference is either fixed in the port (its own commit, named as a behaviour fix) or listed as a named adjustment the owner approved. Never widen a tolerance to absorb one.
6. Named adjustments (the only ones allowed in M0, each counted in the report): `software-candle-is-firmware-candle`, `fade-off-to-on-gradual`, `effect-reselect-keeps-running`, `power-on-fade`. Inputs touching Breathe or Colour loop are never generated and lamps running them are excluded.
7. Inputs only the new system handles (Zigbee2MQTT frontend change, stray group command, missed message, power-loss reset) are not fuzzed in M0.
8. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Work happens in `/home/jonathan/worktrees/smarthome-json-edges`, branch `ts-port/json-edges`, workers commit only; the controller pushes to both `feature/typescript-lighting-scripts` and `ts-port/json-edges`.
9. Each new Python file is checked with `python3 -m py_compile` and its unit tests after every edit; `npm run check` and `npm test` stay green.
10. Long runs (golden, fuzz, the old parity) run detached with `systemd-run --user` and `~/.claude/scripts/wait-for`, logs in `/tmp/v1work/`.

## Review Focus

1. **Write-back loops.** The world writes light and switch states back into HA, which fires state triggers, which may send again. Expect: settle stops at quiescence; a loop beyond `SETTLE_LIMIT` steps fails with the last 10 inputs named, never hangs. Test in Task 4.
2. **Group sends.** A Zigbee2MQTT group topic or an HA light group must change every member bulb, and only those. Test in Task 2.
3. **Candle ending.** After the firmware candle starts, a later On or brightness move ends it; a colour-only send does not. Test in Task 2.
4. **Calendar edges.** Clock advances that cross midnight, a weekday→weekend boundary and a DST change (last Sunday of March and October, Europe/Stockholm) must give the same result on both backends. Golden scenario in Task 5.
5. **HA restart mid-fade.** A `homeassistant` start during a scheduled fade restores from the sensors and lands on the same state on both backends. Golden scenario in Task 5.

### Task 2: World model

**Files:**
- Create: `lighting-scripts/tests/e2e/world.py`
- Test: `lighting-scripts/tests/e2e/test_world.py` (synthetic names only: `bulb_a`, `group_ab`, `plug_x`)

**Interfaces:**
- Produces:
  ```python
  @dataclass(frozen=True) class Kelvin: kelvin: int
  @dataclass(frozen=True) class Rgb: r: int; g: int; b: int
  Colour = Kelvin | Rgb
  @dataclass(frozen=True) class Off: pass                                  # off has no level and no colour
  @dataclass(frozen=True) class On: level: int; colour: Colour | None; effect: Literal['none','candle']   # colour None only before any colour was ever sent
  BulbState = Off | On
  @dataclass(frozen=True) class BulbInfo: topic: str; candle_capable: bool
  @dataclass(frozen=True) class Line: start: BulbState; end: BulbState; t0: float; t1: float   # a transition in progress; a fade from Off ramps from level 0, a fade to Off ramps to 0 then is Off at t1
  class World:
      def __init__(self, bulbs: Mapping[str, BulbInfo], groups: Mapping[str, list[str]], switches: list[str], ha_lights: Mapping[str, list[str]]): ...
      def apply(self, call: dict, now: float) -> None          # one recorded DrySim call
      def bulb(self, name: str, now: float) -> BulbState        # interpolated on an active Line
      def switch(self, entity: str) -> Literal['on','off']
      def press_switch_button(self, entity: str) -> None
      def ha_states(self, now: float) -> dict[str, dict]       # light.* and switch.* as HA state objects
      @staticmethod def from_sim(sim: DrySim) -> 'World'        # membership from the catalog and sim.members
  ```
- Recorded call shape: `{'time','action','target','data'}`; for `mqtt.publish`, `data['topic']` and `data['payload']` (a JSON string — parse it, never compare text).
- Calls handled:
  1. `mqtt.publish` to `zigbee2mqtt/<topic>/set`, where `<topic>` is looked up whole in the catalog's topic table (a device address, a friendly name, or a group topic that may itself contain `/`; never split on `/`). Payload keys: `state` (`ON`/`OFF`), `brightness`, `color_temp` (mired), `color` as `{"rgb": "r,g,b"}` (comma-joined string), `transition`, `effect` ∈ {`channel_change` → candle starts, `stop_effect` and `stop_colorloop` → candle ends}. Any other key or effect value raises `UnhandledPayload`.
  2. `light.turn_on`/`light.turn_off` on HA lights and HA light groups (expanded); `data` may be empty or carry `brightness`, `rgb_color`, `color_temp_kelvin`, `transition`.
  3. `switch.turn_on`/`switch.turn_off`, and `homeassistant.turn_on`/`homeassistant.turn_off` whose `entity_id` mixes lights and switches.
  4. `entity_id` may be a string or a list. Profile lights (`light.ls_*`) are not bulbs: ignored explicitly. A `zigbee2mqtt/` topic or a light/switch entity not in the catalog raises `UnknownTarget`.
  5. Every other action (sensor writes, script calls, events) is not world state: ignored.

### Task 3: Trigger router

**Files:**
- Create: `lighting-scripts/tests/e2e/router.py`
- Test: `lighting-scripts/tests/e2e/test_router.py` (synthetic automation configs)

**Interfaces:**
- Produces:
  ```python
  Input = HaStart | Tick(now: datetime) | StateChanged(entity, old: dict|None, new: dict, context: Context) | Event(type, data, context) | Mqtt(topic, payload) | ScriptCall(script, data, context)
  @dataclass(frozen=True) class Context: id: str; user_id: str | None; parent_id: str | None = None
  @dataclass(frozen=True) class AutomationRun: name: str; trigger: dict   # trigger: plain JSON-safe dict (it crosses the port's RPC)
  @dataclass(frozen=True) class ScriptRun: name: str; data: dict
  Run = AutomationRun | ScriptRun
  @dataclass(frozen=True) class House: automations: Mapping[str, dict]; helpers: Mapping[str, dict]; labels: Mapping[str, list[str]]  # label id → entity ids
  def load_automations(sim) -> dict[str, dict]   # one entry per capture, keyed 'automation_<file stem>' (the key the port's run_automation accepts); drops the id/alias duplicates DrySim also holds
  def route(house: House, inp: Input, previous_tick: datetime | None) -> list[Run]
  ```
- Each automation fires at most once per input, with the first matching trigger. Trigger `id` is the trigger's `id`, or its index as a string when absent; several triggers may share an id.
- Trigger kinds and their rules (all present in the captures); any other kind, or an unknown option on a known kind, raises `UnsupportedTrigger` at load:
  1. `homeassistant` (`event: start`): fires on `HaStart`.
  2. `state`: `entity_id` string or list; `to`, `from` (each a value or a list), `not_to`, `attribute`. With none of `to`/`from`/`not_to`/`attribute`, any state or attribute change fires; with any of them, an attribute-only change does not fire; with `attribute`, it fires only when that attribute's value changes. Trigger dict: `entity_id`, `from_state`, `to_state` (HA state objects).
  3. `time_pattern`: `seconds`/`minutes` with `/n`; fires once for each matching instant in `(previous_tick, now]`.
  4. `time`: `at` is a literal `"HH:MM:SS"`, an `input_datetime` entity (honour `has_date`/`has_time`; no value → never fires), or `{entity_id, offset}`. Fires when the instant falls in `(previous_tick, now]`, in local time (Europe/Stockholm, DST-aware).
  5. `event`: `event_type`, optional `event_data` filter (subset match). Trigger dict: `event` = `{event_type, data, context: {id, user_id, parent_id}}`.
  6. `mqtt`: `topic` with `+` wildcards; optional exact `payload` match; optional `value_template`, rendered through `House.render: Callable[[str, dict], object]` (the backend passes its sim's renderer; truthy result fires). Trigger dict: `topic`, `payload`, `payload_json` (parsed when JSON).
  7. `light.turned_on`: `target.label_id` (entities via `House.labels`); fires on a light's off→on only. Trigger dict: `entity_id`, `from_state`, `to_state`.
- A `ScriptCall` for a dashboard script (`ls_override_block`, `ls_clear_overrides`, `ls_range_save`) returns `[ScriptRun(name, data)]`.
- `ls_override` events emitted by the scripts are never routed: `DrySim.event` already runs the store writer inline.
- A person's light change is two inputs, in HA order: `Event('call_service', {domain, service, service_data}, Context(id=<new>, user_id='person'))`, then the resulting `StateChanged`s from the world.
- The router is backend-blind: it routes every captured automation on both backends. A run the port has no handler for is the backend's concern (Task 4).

### Task 4: Runner and comparator

**Files:**
- Create: `lighting-scripts/tests/e2e/runner.py`, `lighting-scripts/tests/e2e/backend.py`, `lighting-scripts/tests/e2e/compare.py`
- Test: `lighting-scripts/tests/e2e/test_runner.py`, `lighting-scripts/tests/e2e/test_compare.py`

**Interfaces:**
- Consumes: Task 1 `open_sim`, `reference_available`, Task 2 `World`, Task 3 `route`, `Input`.
- Produces:
  ```python
  Step = Input | Advance(seconds: float) | PressSwitch(entity) | PersonLightChange(entities: list[str], service_data: dict)
  @dataclass(frozen=True) class Checkpoint: t: float; bulbs: dict[str, BulbState]; switches: dict[str, str]; dashboard: dict; in_fade: frozenset[str]
  def run_backend(backend: Literal['reference','port'], steps: Sequence[Step], start: datetime) -> list[Checkpoint]
      # spawns one subprocess per backend (`python3 -m tests.e2e.backend <backend>`), sends steps and start as JSON,
      # reads checkpoints back as JSON; inside, `open_sim` + World + route run the scenario. One checkpoint after
      # each step settles, plus fade samples.
  SETTLE_LIMIT = 200
  def compare(a: list[Checkpoint], b: list[Checkpoint], adjustments: Adjustments) -> list[Difference]
  @dataclass(frozen=True) class Difference: t: float; subject: str; field: str; reference: object; port: object
  ```
- `Advance` moves the clock in 60 s ticks (the old engine's cadence) and routes a `Tick` per tick; sub-minute `time_pattern`s are routed for each crossed instant. After every routed run: apply new calls to the world, `drain_output()`, feed world state changes back as `StateChanged` (context `None`), repeat until no new calls. More than `SETTLE_LIMIT` rounds raises `SettleLoop(last_inputs)`.
- Fade samples: for each bulb with an active `Line` longer than 60 s, checkpoints at its start, middle and end; `in_fade` marks them so `compare` uses `MID_FADE_LEVEL_PCT`.
- Software candle (reference): a lamp whose `sensor.ls_effects_runtime` assignment is Candle is reported as `effect='candle'` with its base colour; frames from `effects_engine` are not applied to the world (adjustment `software-candle-is-firmware-candle`). The reference's `effects_engine` is not run.
- Port runs with no handler (captured automations the port does not implement): the port backend records each as `NotPorted(name)` instead of raising, and the checkpoint lists them; `compare` reports them in the summary so triage sees which differences they explain. The reference runs every routed automation.
- Plugs: before `World.from_sim`, the backend seeds the system-controlled `switch.*` entities into `sim.state` from the captured switch-range and schedule config (ruling 11).
- A fade from `Off` reports `On(level=0)` at exactly `t0`; checkpoints at `t0` treat it as a mid-fade sample.
- `Adjustments` is a registry of the named adjustments from Global Constraints 6; each match is counted; `compare` returns the counts with the differences.
